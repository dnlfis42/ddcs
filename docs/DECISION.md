## 동시성은 싱글 스레드 리액터 하나로 처리합니다

모든 상태를 한 스레드만 접근하면 락과 atomic이 사라지고 도메인 로직을 순차적으로 추론할 수 있으며, 워크로드가 I/O bound라 코어 하나로 충분하다는 점은 sweep 실측이 뒷받침합니다.
thread-per-connection은 비용이 연결 수에 비례하고, 멀티스레드 리액터는 Group 집계에 동기화를 되살리며, io_uring은 completion 기반이라 readiness 기반인 현재 구조를 그대로 옮길 수 없습니다.
대신 콜백 하나가 블로킹하면 루프 전체가 멈추고, 코어가 여러 개여도 하나만 사용합니다([한계점](ARCHITECTURE.md#102-제약과-개선-방향)).

## wire 프로토콜을 직접 설계합니다

스트림 위에서 message 경계를 만드는 문제를 직접 다루는 것이 이 프로젝트의 학습 목표이고, payload가 작고 스키마가 안정적이라 length-prefix 프레이밍과 자체 코덱으로 충분합니다.
protobuf는 프레이밍 문제를 그대로 남기고 코드 생성을 요구하며, gRPC는 HTTP/2 스택 전체를 의존성으로 받아야 합니다.
대신 버전 필드가 없어 스키마를 바꾸면 양측을 동시에 배포해야 합니다([한계점](ARCHITECTURE.md#102-제약과-개선-방향)).

## 같은 DeviceId로 재등록하면 새 연결이 기존 연결을 대체합니다 (kick-old)

재접속의 대부분은 기존 연결이 이미 끊겼는데 Controller가 아직 감지하지 못한 half-open 상태이므로, 새 연결을 항상 채택하면 liveness 제한 시간을 기다리지 않고 곧바로 새 Session을 바인딩합니다.
old-wins나 신규 거부는 이미 끊긴 연결이 제한 시간까지 정상 재접속을 막고, 두 연결을 함께 두면 "Device당 연결 1개" 불변식이 성립하지 않습니다.
대신 uuid가 Agent의 신고값이라 어느 쪽이 원래 Device인지 확인할 수 없으며, 이는 인증 계층이 없다는 [신뢰 경계](ARCHITECTURE.md#101-신뢰-경계)에서 비롯한 한계입니다.

## 명령 전달은 at-least-once에 멱등 명령과 중복 제거를 조합합니다

분산 환경에서 exactly-once 전달은 성립하지 않으므로, 목표 상태를 지정하는 멱등 연산(`set_mode`)을 at-least-once로 전달하고 수신측이 중복을 걸러내면 최종 상태는 한 번 적용된 것과 같아집니다.
전체 이력을 보관하는 중복 제거 테이블은 무한히 증가하는 반면, supersede와 TCP 순서 보장 덕에 깊이 1로 충분합니다.
대신 비멱등 명령 타입을 추가하면 수신측 중복 제거를 그 타입에 맞게 강화해야 합니다([명령 RPC](ARCHITECTURE.md#7-명령-rpc)).

## DeviceShadow는 메모리에만 유지합니다

상태의 원본은 Agent 쪽 Device에 있고 Shadow는 다음 Status 보고로 재구성되는 사본입니다.
파생 상태를 영속화하면 낡은 스냅샷과 새 보고 중 어느 쪽이 기준인지 모호해지고, DB 도입은 싱글 스레드 리액터에 블로킹 I/O를 되살립니다.
대신 Controller를 재시작하면 Shadow와 미결 명령이 사라지고, 재보고로 수렴할 때까지 수 초 동안 제어가 멈춥니다([한계점](ARCHITECTURE.md#102-제약과-개선-방향)).

## 정책 전환은 단일 임계값이 아니라 밴드로 판정합니다

단일 임계값은 평균이 임계 근처에서 오르내릴 때마다 명령을 발행해 잦은 전환을 유발하지만, high/low 히스테리시스 밴드를 두면 결정된 Regime이 평균이 반대쪽 임계를 지날 때까지 유지됩니다.
시간 기반 쿨다운은 모든 전환을 일률적으로 늦추고, PID 같은 연속 제어는 연속 출력을 전제하는데 이 도메인의 출력은 Mode 세 값뿐입니다.
대신 평균이 밴드 안에 머무는 동안에는 부하가 달라져도 Mode가 그대로입니다.

## 주기 작업은 sweep 타이머 하나가 실행합니다

명령 재전송, 만료 축출, 정책 평가가 정해진 순서로 수행되면 상호작용(축출, 명령 기억 폐기, 다음 평가의 재명령)을 한 tick 안에서 추론할 수 있습니다.
작업마다 타이머를 따로 두면 실행 순서가 발화 시각에 따라 달라집니다.
대신 제한 시간 감지 해상도가 tick 주기(기본 1초)로 제한되고, sweep 비용이 Session과 미결 명령 수에 비례합니다([한계점](ARCHITECTURE.md#102-제약과-개선-방향)).

## 소켓은 양쪽 모두 `TCP_NODELAY`로 Nagle을 끕니다

Agent는 명령 하나에 ack와 outcome을 중간 read 없이 짧은 write 두 번으로 연달아 보내는데, Nagle이 켜져 있으면 두 번째 write가 상대의 delayed-ACK(Linux 최대 40ms)까지 커널에 붙잡혀 왕복 시간에 부하와 무관한 수십 ms 꼬리가 생깁니다.
실제로 Agent 쪽 옵션이 빠져 있던 동안 완료 명령의 12%가 21~50ms 구간에 몰리는 이봉 분포가 관측됐습니다([README 지연 시간 절](../README.md#지연-시간)).
두 write를 writev 한 번으로 합치는 대안은 전송 큐의 부분 소비 처리를 다시 써야 해 변경 범위가 크고, 대신 짧은 메시지마다 세그먼트가 하나씩 나가 패킷 수가 늘어납니다.
